# Add ads + Remote Config to an existing Flutter app

`/app-factory:build-app` puts this pattern into every new app by itself. This command is for an app that is already built, or was built without ads. Do the steps in order. The rules — where each ad goes, the wiring, the Remote Config keys, Premium, the tests — are in `${CLAUDE_PLUGIN_ROOT}/skills/flutter-ads/SKILL.md`: read it in full before step 2. The installed files are never rewritten; the app only calls their API. This command adds ads and nothing else: a bug found on the way is reported, not fixed. Everything the app already does must keep working: the backend (`lib/data/`, `lib/domain/`) only gains the calls flutter-ads section 7 allows, no existing test is changed, and every test that passed before still passes — step 9's checks I1–I5 prove it from git and the test results, and P1–P18 prove the ads follow the pattern — IPTV_two's ads implementation as the guide app common_flow_demo runs it.

## 1. Check the folder and the device — stop at the first failure and say why

- `pubspec.yaml` with `flutter:` and an `android/` or `ios/` folder. Otherwise: "Not a Flutter app."
- A git repository with nothing uncommitted (`git status --short` prints nothing). Uncommitted changes → stop: "Commit or stash your changes first, so this change is one commit you can revert." No git repository → say the change cannot be reverted with git and that no `ADS_CHANGES.md` (step 9) can be made, and ask whether to go on.
- Earlier ads work is never patched up — the run starts again from nothing: `node "${CLAUDE_PLUGIN_ROOT}/scripts/ads-install.mjs" reset "$(pwd)"`. It reverts every commit whose subject starts with `app-factory: ads` (newest first, one already reverted is skipped), then removes with `git rm`, in one commit, any template file still in the app (installed by hand or committed under another message) and every file an earlier app-factory version installed (`lib/google_ads_material/`, `test/google_ads_material/`, `assets/remote_config_default.json`, `NativeAdStyle.kt`, `LayoutNativeAdFactory.kt`, `native_small.xml`, `native_big.xml`), so step 4's install copies every file fresh — a kept older copy (`install` never overwrites) was how a stale `app_open_ad_manager.dart` stayed in Live Street View on 2026-10-27. It prints `HEAD <sha>`. With no earlier ads work it prints "nothing to reset". Exit 1 → do not go on: "uncommitted changes" (commit or stash first), or "CONFLICT reverting …" with the files (later commits changed the same lines; the revert was aborted and the tree is clean — tell the user the commit and the files and stop). The app's own older ads layer that an ads commit had replaced comes back with the revert: step 2a lists it again. Then record `git rev-parse --short HEAD`: it is `<base>` in step 9 (with a reset, the HEAD it printed).
- The app's tests as they are, before anything changes: `"<flutter>" test -j 4 -r failures-only --file-reporter json:.dart_tool/ads_tests_before.json`. Quote the result line. A test that fails here already failed before the ads work: report it, do not fix it (step 9's check I3 counts only the tests that passed here).
- CONTRACT.md section 9 quotes a PRD line saying the app has no ads → tell the user and go on only if they confirm. A PRD line that allows only some formats (Live Street View's PRD 4.9: "interstitial only; no banners, no app-open ads, no native ads") → step 3 places only the rows of those formats and lists every other row as "not placed: PRD <section>", unless the user tells you to place the full pattern; then CONTRACT.md section 9 says so ("full pattern placed over PRD <section> on <date>, the user's choice").
- A device with internet, picked without asking anyone: `node "${CLAUDE_PLUGIN_ROOT}/scripts/pipeline.mjs" devices pick android` when the app has `android/`, else `devices pick ios`. Never ask the user which device and never wait for an answer. It returns the first usable connected phone (`"kind":"phone"` — Android woken and, behind a lock screen without a code, swiped open; an iPhone with Developer Mode on), and only when there is none starts the plugin's own device (`"kind":"emulator"` / `"simulator"`); `skipped` names every phone it passed over and why (a code lock, Developer Mode off) — put that line in the report. Use its `serial` / `udid` in every later step. Measured 2026-10-27: the Samsung M04 picked in 0.4 s; with no iPhone connected, `app-factory-iphone-17` started in 61 s. An app launched behind a lock screen never gets focus: `wait-app` then reports not ready.
  **The plugin's own device** (what `devices pick` starts when no phone is usable; `devices up android|ios` alone does the same) — it creates the emulator `af-standard` (or the simulator `app-factory-iphone-17`) when it does not exist, frees memory only by shutting down the plugin's own simulators, starts it in its window, waits until it has booted and settled, and prints `"serial"` (or `"udid"`) — use that id in every later step. Measured on this Mac: created, booted and settled in 132 s; started again in 52–60 s; 0.4 s when it is already running. The whole step 8 passed on it (7 device tests, every placement and exit by hand). It never uses or changes the user's own emulators and simulators. If it fails, its message says what is missing (the system image, Java, memory, disk) — do that, then run it again; there is no other way to get a device. An emulator or simulator has no photos: a picker opens empty, which is enough to check it leaves and returns.
  Android: `pipeline.mjs maestro-install` once (the element list needs it). iOS simulator: `npx -y mobilecli agent install --device <udid>` once per new simulator (mobile-mcp's element list needs it).

## 2. Explore the entire app — before changing anything

Read `${CLAUDE_PLUGIN_ROOT}/skills/app-qa/SKILL.md` rules E2 and E8 first: elements are found and tapped from the element list (Android `read_screen`, iOS mobile-mcp), never by coordinates read off a screenshot; after a launch, `pipeline.mjs wait-app`, never a fixed pause.

**a. From the code — the full list.** Every route, pushed screen, modal, bottom sheet and dialog, each with its file, the screen that opens it and the tap that does. Then: home (the first screen a returning, logged-in user sees); tabs and their roots; the text fields of each screen; a splash screen, onboarding, Premium / paywall screen, store purchase, reward (credits, an unlock); every call that leaves the app — `grep -rnE "Share|share_plus|launchUrl|url_launcher|in_app_review|requestReview|openStoreListing|buyNonConsumable|buyConsumable|restorePurchases|ImagePicker|FilePicker|camera|openAppSettings|mailto:|tel:" lib` (the pattern adds nothing before them — IPTV has no skip, flutter-ads section 8 — but step 8 records what the resume ad does after each). Then the app's own ads and Remote Config code, which the pattern replaces — `grep -rnE "FirebaseRemoteConfig|MobileAds\.instance|(Interstitial|AppOpen|Rewarded|RewardedInterstitial)Ad\.load|BannerAd\(|NativeAd\(|getValue\(" lib | grep -v "^lib/ads/"` — with every value it reads from its own Remote Config key; the purchase check (where it runs) and the rule it uses for Premium; and any connectivity check in front of the startup. Also the app's own ad-tap counter with every line that changes it — `grep -rnE "\b_?(ads?|inter|home|click)[A-Z]?\w*(Flag|Count|Counter)\b" lib | grep -v "^lib/ads/"` — and the app's privacy / consent row (`grep -rnE "PrivacyOptions|privacyOptions|GDPR" lib`). **The app's own ads layer** — the list passed as `--replaced` in steps 8 and 9: every `lib/` file that imports an ads SDK (`grep -rlE "import 'package:google_mobile_ads/" lib`), every `lib/` file that imports one of those to load, gate or show ads (an ads repository, an "ad moment" dialog), every `lib/` file that only they import (ad unit ids, an ads rule), and every test file that imports one of them (`grep -rlE "<file names>" test integration_test`). Live Street View: `data/services/ads_service.dart`, `data/repositories/ads_repository.dart`, `domain/use_cases/ads_rules.dart`, `config/ad_ids.dart`, `ui/features/premium/views/ad_limit_dialog.dart`, their four tests, `integration_test/ads_flow_test.dart` and `test/ui/fakes.dart` (its fake of the repository). An app file at a path the template installs (an app that already has its own `lib/ads/ads_variable.dart`, `lib/ads/ads_load_util.dart`, … — IPTV-style apps do) belongs to that layer: step 4 removes it first, so the installer copies the template's.

**b. On the device — the app as it is now.** `flutter run -d <id>`, then visit every screen of the list once, in the order taps reach it: from launch, through logging in when the app has accounts (a test account from CONTRACT.md, the seed data or the README; none → register one in the app), every tab, every pushed screen, modal and sheet. Tap a text field and wait 1 s before `input text` (typed earlier, the first letters are lost). On a real phone never pick from the owner's photos or files: a screen behind that is mapped from the code and marked so. On each screen read its element list and record: how you got there, every element that opens another screen and which screen it opens, the text fields, every element that leaves the app. One screenshot per screen. After each screen read the app's log (app-qa section 2); an error there goes in the report.

**c. The app map.** Compare a and b: a screen in the code that the device never reached, or one the device showed that the code list missed, is reached the way the code gives — or listed as "not reached" with the reason. The map has one row per screen: screen | reached from (screen, tap) | taps that open another screen | text field | leaves the app. Stop `flutter run`. Write no file.

## 3. Decide every placement from the pattern

Each row of the map gets its row of flutter-ads section 2 — the pattern decides; do not ask the user which taps count or which banner type:
- each tap of the map is classified by the rows of flutter-ads section 2, and the classification is written per tap: **interstitial** only on a Home feature button, on the action after a feature's picker or sheet that opens its screen, and on a content tab item's main action; **no ad** on switching tabs (bottom bar, a button that switches tab, `TabBar` tabs), a recent / history item, premium, settings, credits, sheets, dialogs, pickers, toggles, secondary item actions, help, and every tap inside an inner screen; each interstitial tap goes through `onTapInter(() => <push>)`, and every screen such a tap opens gets IPTV's back rule (`PopScope` … `if (didPop && AdsVariable.homeFlag.isOdd) AdsVariable.homeFlag++;`);
- the Home tab gets one small native below its feature buttons (`NativeAdsWidget(showNativeAd: AdsVariable.nativeAdHome, isSmallNative: true, …)`, loaded once while `AdsVariable.nativeAdHome` is null; IPTV's `config.json` ships `nativeHome` `"11"` = off);
- the banner (`BannerWidget(adsId: AdsVariable.banner, …)`, the last child of the screen's `Column`) goes on a list screen pushed from home or a tab without a text field and not a media player, and on a content tab root; no banner on Home, a collection-management tab, help or Settings tabs, a text-field screen or a player;
- splash (interstitial `interSplash`), intro (big native + intro-finish app open `appOpenIntro`) rows only when the map has that screen; a Premium screen gets no ad and sets `AdsVariable.isShowingAd.value = true` (no resume ad while it is open); Settings gets the privacy options row.

Write the table: screen | ad | trigger / position | Remote Config keys | code | why this row.

## 4. Install

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/ads-install.mjs" "$(pwd)" --no-premium && "<flutter>" pub get
```

First, when step 2a found app files at template paths: `git rm` them (they are listed in `--replaced`). ## 5. Wire

As flutter-ads section 3 says (the guide app's code, which is IPTV's), including its "App shapes" list (no splash screen, `go_router`, no onboarding, no paid tier, tabs). `AdsSplashUtils.remoteConfigKey` is already `<pubspec name>_v1` (the installer writes it). Every placement exactly as the table of step 3:
- `main()`: `AdsVariable.isFirstTimeVisited = prefs.getBool("isFirstTime") ?? false;` before `runApp`; `navigatorKey: AdsVariable.navigatorKey` on the `MaterialApp` / `GetMaterialApp` / `GoRouter`;
- the splash: `AdsSplashUtils.fetchPurchase = <the app's purchase check, setting AdsVariable.isPurchase>`, then `await AdsSplashUtils().getOnlineIds(navigateScreen);` and, online, `AdsLoadUtil().loadInterSplash(loadPreLoadAds, navigateScreen, AdsVariable.interSplash, enable: AdsVariable.sendRevenueToAnalyticsForInterSplash)` — `navigateScreen` and `loadPreLoadAds` as the guide app's `AppFlow` (IPTV `splash_screen.dart:55-96`); the app's own next-screen logic (login, onboarding) goes inside `navigateScreen`;
- Home, first build: `AdsSplashUtils().loadAppLifecycleReactor();` and `prefs.setBool("isFirstTime", true)`; the intro's finish also stores it;
- the startup on every launch, online or offline — a connectivity check in front of `getOnlineIds` (step 2a) is moved behind it, never around it (`getOnlineIds` itself handles offline: stored ids, next screen after 4 s);
- the app's own ads and Remote Config code of step 2a is replaced: its ad loads, SDK start and Remote Config fetch leave the startup and the screens; the files of its ads layer (step 2a) are deleted, and its tests with them — a test file that also tests other things keeps those tests and changes only what faked the old layer (Live Street View's `settings_test.dart` GDPR test: it counts the UMP channel's `showPrivacyOptionsForm` calls instead of the old fake's counter). Each value it read from its own key becomes a key the IPTV way (flutter-ads section 2, "A new placement or key": an `AdsVariable` field, its line in `getOnlineIds` and `setOnlineIds`, the key in `assets/ads/config.json` with the same value) and the app reads `AdsVariable.<key>`. Its purchase check becomes `AdsSplashUtils.fetchPurchase`, unchanged. Report every moved key: the owner publishes it under `<pubspec name>_v1` before release;
- an ads package the app already had at another version is set to the tested version (flutter-ads section 1), then `"<flutter>" pub get`;
- the app's own ad-tap counter of step 2a and every line that changes it are deleted (a `PopScope` that only bumped it goes, its child stays): `onTapInter` and IPTV's back rule on `AdsVariable.homeFlag` replace them;
- a privacy options entry: Settings (or the app's menu when it has no Settings) shows a row only when `AdsVariable.isPrivacyOptionsRequired.value` is true, its tap calling `showPrivacyOptionsForm((formError) {})` (IPTV `setting_screen.dart:127-141`; guide app `setting_screen.dart:48-49`); a row the app already has on its old consent code is pointed at these two, never commented out (P17);
- code under `lib/data/` and `lib/domain/` imports only `ads/ads_variable.dart` and calls only `AdsVariable.isPurchase.value = …` / `AdsVariable.resetAdIds()` (flutter-ads section 7, check I4);
- the intro's own content fits above the big native on every page and every phone: no text drawn over the dots, the button or the native and none cut off — a `Column` whose picture part is `Expanded` (only the picture shrinks), the text, dots and Continue at their own size below it, then the native; or the design's full-bleed art with the page's text in a `SafeArea` scroll view that ends above the bottom area where the dots, the button and the native sit. Not IPTV's `Stack` with everything pinned (`intro_screen.dart:58-150`: they overlap on a short screen) — that is the app's screen layout, not the ads code. Step 8 checks it on a small screen, a large font and landscape.

## 6. Contract (only in an app-factory project: CONTRACT.md and `.pipeline/` present)

- CONTRACT.md section 9: the table of step 3 and one line per screen with no ad and why.
- Section 3: a `### ads` group with one criterion per placement, numbered after the highest existing AC.
- Criteria that described the app's own ads layer of step 2a (Live Street View: AC48–AC50, its ad-limit dialog and gate) are not deleted: each line becomes `- ACn REPLACED by ACm (app-factory ads, section 9): …` and `pipeline.mjs feature <ACn> blocked "replaced by ACm (app-factory ads pattern, CONTRACT section 9)"` takes it out of coverage; one still true of the new layer (Premium: no ads; the consent → ATT → SDK order) stays in the ads group and gets its test in step 7 if its old one went with the layer.
- Section 5: `ads — AC…` as the last group.
- Register them: `node "${CLAUDE_PLUGIN_ROOT}/scripts/pipeline.mjs" feature <ACn> failing "<criterion title>"` for each, then `… group ads <ACn…>`; after step 8 passes, `feature <ACn> passing` for each.

## 7. Tests

The installed `test/ads/ads_test.dart` and `integration_test/ads_device_test.dart` stay as they are. Per criterion one widget or unit test whose name starts with its id ("AC47 …") and checks the wiring in the app's own screens, with the SDK not started (mock the `dev.fluttercommunity.plus/connectivity`, `PonnamKarthik/fluttertoast` and `nativeChannel` channels as `test/ads/ads_test.dart` does):
- the ad widget is on its screen (`BannerWidget`; `NativeAdsWidget` once `AdsLoadUtil.isNativeAdLoaded.value = true`) and absent on the screens the table excludes;
- a home feature tap goes through `onTapInter`: with `AdsVariable.interPreLoad` set and `AdsVariable.homeFlag = 1` the screen opens at once and `homeFlag` becomes 2; Back from that screen with an odd `homeFlag` makes it even;
- with a paid tier: `AdsVariable.isPurchase.value = true` → no native or interstitial (IPTV draws banners for Premium too — flutter-ads section 8 — so a banner test does not check Premium);
- the launch step, in `integration_test/`, when the app's splash differs from the guide app's.

## 9. Record what changed, then commit

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/ads-install.mjs" changes "$(pwd)" <base> --replaced <the same list as step 8>
```

`--replaced`: each file is proved from `<base>` — it imports an ads SDK or another listed file, or (`lib/`) only listed files import it; a file that cannot be proved fails I1 with the reason. Proved files are left out of I1, I2 and I4, and their tests out of I3's "no longer runs" (a test that still runs must still pass); the report lists them under "Replaced: the app's own ads layer".

It writes `ADS_CHANGES.md` in the app from git (every file added, changed or deleted since `<base>`, committed or not, with its diff), the template (each installed file checked byte for byte against it) and the code (every line of the app's own `lib/` that uses the ads layer, as file:line), and prints its summary lines. Never edit it by hand and never write it yourself — rerun the command after any later change. A template file marked **differs from the template** whose diff is not one of flutter-ads section 2's allowed additions (a new key in `ads_variable.dart`, `ads_splash_utils.dart`, `assets/ads/config.json`) is a mistake: restore it and run the command again.

Its **Checks** section, near the top, is each rule checked by the command, PASS or FAIL with the file:line lines behind it; the command exits 1 when one fails. I = the app as it was still works: I1 only files the ads work owns were touched; I2 no test that existed before was changed or deleted; I3 every test that passed in step 1 passes in step 8 (from the two `.dart_tool/ads_tests_*.json` files); I4 the backend keeps every line it had and gains only an import of `ads/ads_variable.dart` and `AdsVariable.isPurchase.value = …` / `AdsVariable.resetAdIds()`; I5 `pubspec.yaml` keeps every line (no existing package or version changed). Every check must PASS before the commit. A FAIL is fixed in the wiring (never by changing the backend, an existing test or an installed file, and never by editing the report), then steps 8.1–8.2 and this command run again.
